# MDU-56 — Port the grok agent profiles to the pi harness (design)

- **Status:** design complete, ready for implementation.
- **Inputs:** MDU-56 pi research report (`pi-research.md`, session tmp — citation-
  backed, authoritative for every pi fact below, cited as "§N"); `grok/agents/*.md`
  (20 profiles); `scripts/build.sh` + `scripts/lib/validate.py`; backlog MDU-56 ACs.
- **pi version:** `@earendil-works/pi-coding-agent` 1.5.2 (earendil, not legacy
  mariozechner).

## User decisions (closed, do not re-open)

- **D-U1** The port lives in the **base repo** (generic, usable by any pi user).
- **D-U2** Install into the user's `~/.pi/agent` (`pi install ./local` or equivalent
  persistent mechanism) is **pre-approved** once artifacts exist and pins pass.
- **D-U3** **xai-only** — pi has only the xai provider authenticated.

## pi facts relied on (research-verified)

1. No sub-agents, no named-persona registry, no permission system (§4, §6). Tools:
   read, bash, edit, write, grep, find, ls (+powershell); no TodoWrite, no question
   tool; MCP possible via `mcp.json`, not configured by default (§6).
2. Prompt templates: `<agent-dir>/prompts/` direct `.md` children; frontmatter keys
   `description`, `argument-hint`; invoked `/name args`; `$ARGUMENTS`/`$1` substitute;
   expanded before text reaches the model (§2).
3. Packages: a plain dir with conventional `prompts/` (+skills/extensions/themes)
   subdirs; `pi install ./local` persists via `~/.pi/agent/settings.json`; optional
   `package.json` manifest with a `pi` key + `"keywords": ["pi-package"]` (§3).
4. User's `settings.json` already pins `defaultProvider: xai`, `defaultModel:
   grok-4.7` — same as pi's built-in default; non-default per run via `--model
   xai/<id>`; `--list-models` enumerates the catalog (§5).
5. One-shot `pi -p "msg"` writes final text to stdout. `/template args` as the
   message expands the template — **code-verified but docs-UNVERIFIED** (§8); smoke
   proves it live.
6. Isolation: `PI_CODING_AGENT_DIR` redirects the whole agent dir; per-run
   `--prompt-template <path>` loads without install; `-ne`/`--no-mcp`/
   `--no-session`/`-na` trim the surface; no `--isolated` flag (§1, §7, §8). An
   isolated dir has no `auth.json` → auth via env `XAI_API_KEY` (§5); never print it.

## D1 — Artifact shape: one pi package of role prompt templates

**Decision.** A single pi package generated at build time into `build/pi/`: one prompt
template per profile (`build/pi/prompts/<role>.md`) plus a generated `/roster` template
listing roles, argument hints, model notes. Installed persistently via
`pi install ./build/pi` (pre-approved, D-U2). UX: `/just-code <brief>`,
`/orchestrator <task>` …; `$ARGUMENTS` carries the brief into a trailing `## Task`
section.

**Rationale.** Templates are pi's only first-class, discoverable, zero-code surface for
"load this role's instructions now": auto-discovered, `/`-menu visible, args substitute
into the prompt, install once. The role body becomes the session's working
instructions — an acceptable equivalent of a subagent system prompt given fact 1 plus
the adapter preamble (D2).

**Rejected.** *Skills per role:* all 20 names+descriptions inject into the system
prompt at startup (bloat) and bodies load lazily only if the model chooses —
non-deterministic role adoption; wrong fit for "be this role now". *TypeScript
sub-agent extension* (upstream `examples/extensions/subagent/`): real code, not a
prompt port; out of scope, possible follow-up. *Per-run `--system-prompt <file>`
recipes as primary:* strongest placement but no discovery/install story; kept as a
power-user fallback in `pi/README.md` (same generated files).

## D2 — Body adaptation: adapter preamble + verbatim body

**Decision.** Deterministic 5-part template; the source body is copied
**byte-verbatim** (zero prose edits). All adaptation lives in a shared hand-authored
preamble that explicitly wins conflicts:

```
---
description: "<source description verbatim> (pi port)"
argument-hint: "<per-role hint from pi/port-config.json>"
---
<!-- generated by scripts/lib/gen_pi_templates.py; DO NOT EDIT -->
<pi/adapter-preamble.md verbatim>
**Model note:** <generated from source frontmatter model — mapping below>
<grok/agents/<role>.md body, byte-verbatim, frontmatter stripped>

## Task

$ARGUMENTS
```

**Frontmatter mapping.** `name` → filename / `<name>` invocation. `model` → a body
model note (template frontmatter supports only description/argument-hint, fact 2):
- `grok-4.7` → "Intended model xai/grok-4.7 — pi's default; no flag needed."
- `grok-build-0.1` → "Intended rung grok-build-0.1 (bulk). Verify with
  `--list-models`; if pi's xai catalog lacks it, run on the default xai/grok-4.7 and
  note the cost delta. Never block on model choice." (Catalog availability unknown —
  **verify live**, smoke phase 2; the design does not depend on it.)

**`pi/adapter-preamble.md` required clauses** (implementer writes; Gate E pins):
1. Harness delta: pi toolset is read, bash, edit, write, grep, find, ls; no TodoWrite, no
   question tool, no sub-agents, no permission gate (allowlists are config, not
   approval).
2. Delegation reframe: where the profile says delegate/dispatch/spawn to agent X —
   either perform that phase yourself in this session following X's profile discipline
   (interactive: invoke `/x` to load it), or produce a brief for the user to run
   `/x <brief>` in a fresh pi session. **This preamble overrides conflicting
   harness-specific instructions in the body.**
3. Inert mechanics: OpenCode env vars/session ids, Ctrl+X keybindings, `/compact`,
   `opencode api` calls, cache-miss/compaction gates, literal step counters — skip the
   mechanics, keep the intent (checkpoint durable work; don't bloat context; wrap up
   when effort is high).
4. MCP: if a referenced MCP tool (e.g. Playwright) is not configured in pi, follow the
   profile's own fallback discipline (qa: BLOCKED).
5. Everything harness-agnostic (safety gates, retry caps, token frugality, secret
   discipline, run-ledger contract, `.agents/memory/`) ports as-is and stands.

**Why preamble-over-prose-edits.** Deterministic (no regex surgery on 20 evolving
prompts), drift-proof (Gate B asserts body bytes equal source bytes), and future
source edits flow into the port automatically. Trade-off: bodies still *contain*
unexecutable instructions; the precedence clause resolves that, parity records it.

**Parity notes.** `docs/pi-parity.md` is hand-curated, one row per (construct,
profile) hit: *construct · profiles · disposition* — `reframed-by-preamble` /
`ports-as-is` / `dropped (reason)` / `verify-live`. The generator's `--audit` mode
emits hits from a construct lexicon in `pi/port-config.json` (delegation family,
TodoWrite, question tool, MCP/Playwright/blender, OpenCode env vars,
keybindings//compact, shell-allowlist mentions, model tables); a test enforces every
hit has a row. Known limit: a *new* construct class matching no lexicon term is not
auto-detected — the golden-refresh checklist (D4) requires diff review and lexicon +
parity extension when new harness-specific lines appear.

## D3 — Generator, hooked into the existing build

**Decision.** A generator, not static artifacts: `scripts/lib/gen_pi_templates.py`,
invoked from `scripts/build.sh` right after Claude-agent generation (same pattern as
`gen_claude_agents.py`: output into gitignored `build/pi/`, never hand-edited). Reads
`grok/agents/*.md` + `pi/port-config.json`; emits `build/pi/` = `package.json` (name
`open-agent-definitions-pi`, version pinned in config — no timestamps ever, or
idempotency breaks; `keywords: ["pi-package"]`), `prompts/` (20 roles + `/roster`),
and `PARITY.md` (renders audit hits + config dispositions; ships in the package so
installed users see it). `--audit` prints the JSON hit list for tests.
`scripts/lib/validate.py` gains a light `validate_pi_package()` (21 prompt files,
frontmatter parses); full pins live in tests (D4).

**Rationale.** This repo edits prompts every MDU under a regression gate; static
byte-pinned artifacts would rot on the next prompt edit. Generation from the single
source (`grok/agents/`) keeps one canonical prompt per role, matching the repo's
mirrors-from-one-source discipline. Standalone script rejected: a step outside
`./build.sh` gets forgotten; the hook guarantees `build/pi/` always reflects current
sources, and the golden gate forces the tracked snapshot to be refreshed deliberately.

## D4 — Parity gates in-repo (pinned by test-agent)

New `tests/test_mdu_56_pi_port.py` + golden snapshot `tests/fixtures/pi_golden/`
(tracked; mirrors `build/pi/` — `package.json`, `prompts/*.md`, `PARITY.md`):

- **Gate A (shape):** 20 sources → 20 role templates + `/roster`; filenames = source
  `name`s; every frontmatter has non-empty `description` + `argument-hint`;
  descriptions = source description + ` (pi port)`.
- **Gate B (verbatim body):** each template contains the exact bytes of its source
  profile's body (frontmatter stripped) — no silent prose drift.
- **Gate C (golden + idempotency + drift):** regenerate into a temp dir twice →
  byte-identical (idempotent) and byte-equal to the golden; any `grok/agents/` or
  `pi/` change without a deliberate golden refresh turns this red. Refresh flow
  (mirrors the prompt-regression baseline discipline): after a QA-validated
  intentional change, regenerate, review the diff (extend lexicon + parity rows for
  any new harness-specific line), commit golden + parity together.
- **Gate D (parity coverage):** every `--audit` hit (term × profile) has a row in
  `docs/pi-parity.md`; unmapped hit → red.
- **Gate E (preamble):** every template contains the five clause headings and the
  precedence sentence.

## D5 — Smoke plan (devops; all commands `timeout`-wrapped)

**Phase 0 — no pi, no `~/.pi` touched.** `./build.sh` green; pytest green;
`build/pi/` holds 21 templates.

**Phase 1 — isolated expansion proof (verify live; docs-UNVERIFIED, fact 5).**
Prep: `mkdir -p /tmp/opencode/mdu-56/pi-smoke`. Needs `XAI_API_KEY` exported — never
print it. If the key is unavailable to the shell, fallback: copy the real agent dir
to the tmp dir *minus* `sessions/` — still touches nothing in `~/.pi`.

```
PI_CODING_AGENT_DIR=/tmp/opencode/mdu-56/pi-smoke \
PI_CODING_AGENT_SESSION_DIR=/tmp/opencode/mdu-56/sess \
XAI_API_KEY="$XAI_API_KEY" timeout 90 pi -p --no-session -na -ne --no-mcp \
  --prompt-template build/pi/prompts/just-code.md \
  "/just-code In one line, state your agent name and intended model, then reply OK"
```

Pass: the reply names **Just Code** and the model note — impossible if `/name`
expansion failed in print mode (a bare "/just-code …" message would not identify the
role). Repeat with `/orchestrator` (must name Orchestrator) and check `$ARGUMENTS` via
`/just-code Echo the text under your Task heading verbatim`. If expansion fails:
record it, use `--system-prompt build/pi/prompts/<role>.md` one-shots for phase-2
role checks, and note in parity docs that `/name`-in-print-mode needs a pi fix.

**Phase 2 — real install + orchestrator/coder on xai (pre-approved, D-U2).**

```
timeout 60 pi install ./build/pi      # from repo root
timeout 30 pi list                    # confirm package + prompts registered
timeout 30 pi --list-models xai       # record catalog: is grok-build-0.1 there?
timeout 90 pi -p "/roster Reply with the first role name on the roster, then OK"
timeout 90 pi -p "/orchestrator In one line, state your agent name, then reply OK"
timeout 90 pi -p "/just-code In one line, state your agent name, then reply OK"
timeout 90 pi -p --model xai/grok-4.7 "/just-code state your role name, then reply OK"
```

Pass: all replies identify their role; the last proves `--model` guidance. Record
(verify live) whether `pi install ./local` **copied or referenced** the gitignored
`build/pi/`; if referenced, note "re-run `pi install` after each rebuild" in
`pi/README.md`. If local-dir install misbehaves: pre-approved fallback = copy
`build/pi/prompts/*.md` into `~/.pi/agent/prompts/` (auto-discovered, fact 2). Role
name collisions with pre-existing user templates (verify live) are resolved by
renaming in `port-config.json`, never by editing the user's files.

## D6 — Scope edges

- **grokestrator + overlay `grok-*` family:** **defer** — overlay-owned, personal
  (D-U1); generator is overlay-reusable later. Follow-up backlog note, not this MDU.
- **qa/qa-pro Playwright-or-BLOCKED:** ports as-is. pi supports MCP via `mcp.json`;
  if Playwright is configured there it works, else the body's own BLOCKED discipline
  fires — harness-agnostic by design. Parity row: `reframed-by-preamble` (clause 4).
- **blender MCP:** overlay-only, absent from base profiles — out of scope entirely.
- **introspector:** ships; parity row marks session-tree forensics as reduced (pi
  sessions are JSONL under the agent dir; session-id clauses inert, clause 3).
- **devops:** ports as-is (bash tool exists; AWS/deploy gates harness-agnostic).
- **repo `skills/` in the package:** out of scope; pi natively discovers
  `~/.agents/skills/` (§2) — a later MDU can ship base skills cheaply.
- **Model ids:** the design relies only on `xai/grok-4.7` (user-pinned default, fact
  4; re-proven live in phase 2). `grok-build-0.1` is never a hard dependency.
